[[ADR-EMG-001]]
== ADR-EMG-001: Generate architecture decision records separately from the main architecture document

Status:: accepted
Date:: 2026-04-29

=== Context

Architecture decision records explain why durable model and generator choices were made.
The main architecture publication should stay focused on the current structure, views,
and evidence instead of embedding the full decision history inline.

=== Decision

Model architecture decision records as first-class authored data and generate them into
a separate Architecture Decision Records document. The main architecture document links
to the generated decision records document through a compact decision index.

=== Consequences

- The main architecture document remains focused on current architecture and traceability.
- Decision rationale remains reviewable as structured model content.
- Generation workflows need a separate decisions output alongside the main AsciiDoc output.

[[ADR-EMG-002]]
== ADR-EMG-002: Keep architecture decision records model-authored and separate from code links

Status:: accepted
Date:: 2026-04-29

=== Context

Architecture decision records capture durable reasoning about model and generator choices.
Linking decisions directly to implementation files would create noisy trace paths and imply
code-level ownership that decisions are not meant to carry.

=== Decision

Store architecture decision records as first-class authored model data with required context,
decision, status, date, and consequences. Do not add code-link fields to the ADR model.

=== Consequences

- ADRs remain focused on architectural rationale instead of implementation inventory.
- Code traceability continues to use requirement and owner markers.
- Main architecture outputs can link to ADRs without embedding code-level decision links.

[[ADR-EMG-003]]
== ADR-EMG-003: Render Gemara as a first-class output using the official go-gemara SDK types

Status:: accepted
Date:: 2026-06-27

=== Context

OpenSSF Gemara is a layered GRC engineering model with published CUE schemas and a Go SDK.
The engineering model already captures controls, threats, risks, attack vectors, functional
units, verification evidence, and POA&M items, which align with Gemara's L1-L3 catalogs, the L5
evaluation log, the L6 enforcement log, and the L7 audit log. We needed a way to emit Gemara that
is guaranteed structurally correct rather than a hand-written approximation.

=== Decision

Build Gemara documents from the official go-gemara SDK structs (github.com/gemaraproj/go-gemara)
and serialize them with the same YAML codec the SDK uses. Treat Gemara as a first-class rendering
with a library API, an enggemara CLI, an AsciiDoc chapter, and MCP tools. Validate every artifact
two ways: load it back through the SDK loader/type discriminator in tests, and run cue vet against
the published Gemara schemas.

=== Consequences

- Output is guaranteed to match the Gemara schemas and is consumable by other Gemara tooling.
- engmod takes a dependency on go-gemara (and transitively go-oscal) for the export path.
- The L5 evaluation log validates via the schema and SDK type discriminator but is not round-tripped through the SDK loader, because its AssessmentStep is a func type that serializes to a name string yet cannot be unmarshaled back.

[[ADR-EMG-004]]
== ADR-EMG-004: Source the Gemara evaluation log from authored control verifications, with pass and fail outcomes

Status:: accepted
Date:: 2026-06-27

=== Context

A Gemara L5 evaluation log is meant to carry the opinionated result of assessing each control,
including passing assessments. The existing OSCAL assessment results path intentionally records
only non-passing findings, so it is a lossy source for an evaluation log.

=== Decision

Build the evaluation log from authored control verifications, which carry both pass and fail
statuses, mapping each verification to an assessment log under its control's evaluation. Synthesize
a needs-review assessment for controls that have no authored verification.

=== Consequences

- The evaluation log faithfully represents pass and fail outcomes rather than failures only.
- Inferred-from-tests verification can later augment this source without changing the contract.

[[ADR-EMG-005]]
== ADR-EMG-005: Keep hand-written OSCAL SSP/AR/POA&M; add Gemara-to-OSCAL only as an additive bridge

Status:: accepted
Date:: 2026-06-27

=== Context

The go-gemara SDK converts a Gemara control catalog to an OSCAL Catalog and a Gemara evaluation log
to OSCAL Assessment Results. It does not produce an OSCAL System Security Plan or Plan of Action and
Milestones, and it does not carry system characteristics, POA&M items, or compliance-profile-resolved
reviewed controls with engmod's deterministic UUID scheme.

=== Decision

Retain engmod's hand-written OSCAL SSP, Assessment Results, and POA&M exporters unchanged. Expose the
Gemara-to-OSCAL conversion as an additive option on enggemara, emitting a Gemara-sourced OSCAL control
catalog (which engmod did not previously produce) and OSCAL assessment results.

=== Consequences

- No information is lost; the same compliance problems remain solved by the existing OSCAL outputs.
- A new Gemara-sourced OSCAL control catalog becomes available for catalog-centric workflows.
- There are now two OSCAL assessment-results paths; the engmod-native one stays authoritative.

[[ADR-EMG-006]]
== ADR-EMG-006: Synthesize Gemara structure that the model does not author, with explicit fallbacks

Status:: accepted
Date:: 2026-06-27

=== Context

Several Gemara constructs are required by the schemas but are not first-class in the engineering
model: per-control assessment requirements and applicability groups, threat capability references,
and risk severity, category, and appetite. Some of these are organizational inputs that cannot be
inferred from the technical model.

=== Decision

Synthesize the missing structure deterministically: assessment requirements from control
verifications (or a default requirement); applicability groups from functional units plus an
all-systems catch-all; threat capabilities from appliesTo with a synthetic system capability
fallback; risk severity derived from likelihood and impact; and a default risk category carrying an
authored appetite. Keep generated artifacts reproducible by stamping dates only from an explicit option.

=== Consequences

- Every artifact is schema-valid without requiring intrusive changes to the authored model.
- Risk appetite and applicability remain coarse until authored as first-class model inputs.
- A future model reshape can replace synthesized fields with authored ones without changing the export.

[[ADR-EMG-007]]
== ADR-EMG-007: Attach trace and model-link markers to package-level var and const declarations

Status:: accepted
Date:: 2026-06-27

=== Context

The Go code scanner originally treated only functions, methods, and types as declaration-level
trace targets. Markers placed before package-level var and const declarations (for example template
and pattern variables) did not attach and were reported as trace_unattached warnings, so their
linking intent was lost and the repository could not reach a fully clean strict-linking scan.

=== Decision

Treat package-level var and const declarations as declaration kinds that attach TRLC-LINKS and
ENGMODEL-LINKS markers, while keeping only functions and methods trace-required. Stray markers that
precede no declaration (for example a trailing marker at end of file) are still reported as unattached.

=== Consequences

- Existing var/const markers now link to the model, giving full linking and a warning-free scan.
- Functions and methods remain the only declarations that must carry a TRLC-LINKS marker.
- The scanner policy test was updated to detect stray markers via a non-declaration position.

[[ADR-EMG-008]]
== ADR-EMG-008: Model multi-repository work as a recursive system-of-systems

Status:: accepted
Date:: 2026-06-27

=== Context

DO-178C governs software only; the hardware and software platforms and their connections are
allocated at the system level (ARP4754A) above the software (DO-178C) and hardware (DO-254)
processes. The engineering model needs to represent system requirements, architecture, hardware,
and the hardware/software interface, and to compose software components that may live in
subdirectories or in separate repositories.

=== Decision

Treat every model uniformly as a system. A system may reference and allocate to subsystem models,
which are themselves systems, recursively to any depth. Software and hardware items are leaf systems
where the DO-178C and DO-254 lifecycle data attaches. There are no fixed system/software/hardware tiers.

=== Consequences

- One model shape composes at every level; existing single-model projects are simply leaf systems.
- Requirement flow-down across systems mirrors ARP4754A allocation.
- Composition is additive and backward compatible with existing models.

[[ADR-EMG-009]]
== ADR-EMG-009: Subsystem references are downward-only with parent-owned allocation

Status:: accepted
Date:: 2026-06-27

=== Context

A subsystem may be reused under many different parent systems and must not depend on any of them.
Allocation and binding must live where the integration happens.

=== Decision

A subsystem never references or is aware of its parents. A parent system declares which subsystems it
uses and how it allocates its requirements onto them. Subsystems expose a provides-and-requires
contract with a public surface distinct from internal identifiers; parents bind only to the public
contract and must satisfy each required interface.

=== Consequences

- Subsystem repositories are reusable and parent-agnostic.
- The reference graph is a parent-to-child directed acyclic graph; cycles are rejected.
- Validation has a standalone scope (the subsystem alone) and a composed scope (the bindings).
- Amended by ADR-EMG-022 and ADR-EMG-023 (v0.8.0); a child still never references its parents, it now traces its own requirements up to its contract items (realizes), and the parent records requirement links in its own repository instead of allocations.

[[ADR-EMG-010]]
== ADR-EMG-010: Resolve subsystem references from local subdirectories first

Status:: accepted
Date:: 2026-06-27

=== Context

Composition should be proven within a single repository before adding cross-repository plumbing, and
certification evidence must be reproducible and resolvable offline.

=== Decision

The reference resolver supports local subdirectory paths and external git repositories. A git
subsystem is cloned once into the workspace .engmod cache (gitignored, treated as temporary), pinned to
an optional revision, and then resolved exactly like a local subsystem; an existing clone that points
at the same repository is reused without network access, so a build is offline-reproducible after the
first resolve.

=== Consequences

- The same resolver serves a monorepo and multi-repository layouts.
- Composed snapshots are reproducible; pin a revision for an exact one.
- Air-gapped certification environments remain supported once the .engmod cache is populated.

[[ADR-EMG-011]]
== ADR-EMG-011: Requirements carry no tiers; delegation is the link

Status:: accepted
Date:: 2026-06-27

=== Context

Requirement levels (system, high-level, low-level) are confusing across a system boundary: a parent
system's low-level requirement would point at a subsystem's system-level requirement, mixing tier
meanings between two models. The link itself already says whether a requirement is delegated.

=== Decision

Requirements carry no tiers. A requirement is either delegated to a subsystem through a downward
composition allocation or implemented here; the presence or absence of a delegation link is enough to
tell the two apart. Linking one requirement to another inside the same document is flagged, because it
recreates the tier coupling this decision removes.

=== Consequences

- Requirement documents stay flat and boundary-agnostic.
- Delegation is expressed once, by the integrating system's downward allocation.
- Internal requirement-to-requirement links are reported instead of silently accepted.
- Amended by ADR-EMG-022 (v0.8.0); delegation is now a requirement link (reqLinks) from the parent requirement to a published contract item of the child, pinned and fingerprinted; composition.allocations is deprecated. Requirements still carry no tiers.

[[ADR-EMG-012]]
== ADR-EMG-012: Trace links are existence-checked, scoped to the owning model, and exported as a matrix

Status:: accepted
Date:: 2026-06-27

=== Context

Code trace markers (TRLC-LINKS to a requirement, ENGMODEL-LINKS to a model element) were only
shape-checked by a regex, so a link to a deleted or mistyped id passed silently. In a monorepo the code
root can also contain other models' code (each example carries its own architecture.yml), whose markers
reference their own requirements, not the model being generated.

=== Decision

Every code trace link is existence-checked against the model: a dangling requirement or model-element
link is an error, and a requirement traced by no code, verification, or delegation is reported as an
orphan warning. Code is attributed to the model whose architecture.yml is its nearest enclosing root,
so a parent model never validates or counts a child model's links. The consolidated trace is also
emitted as a machine-readable matrix (req to code, verification, and delegated subsystem requirement).

=== Consequences

- Trace links are trustworthy, not merely well-formed; the matrix is a real artifact, not prose.
- Monorepos with multiple models validate cleanly without cross-model false positives.
- Orphan coverage gaps are visible without breaking the build.

[[ADR-EMG-013]]
== ADR-EMG-013: CI enforces the generation gates and artifact freshness

Status:: accepted
Date:: 2026-06-28

=== Context

The tool's gates — engdoc errors, trace-link integrity, EARS lint, composition checks, and Gemara
schema validity — and its committed generated artifacts only have value if they are enforced. CI
previously ran gofmt, vet, and unit tests only, so a model edit that broke generation or left the
committed documents stale could merge green. Enforcing artifact freshness also requires generation to
be deterministic.

=== Decision

A single gauntlet (scripts/validate-all.sh) runs in CI and locally. It regenerates every model's
documents — engdoc must exit clean, which enforces trace integrity, dangling links, EARS, and
composition — exports each trace matrix with engtrace (no dangling links), fails on any drift between
regenerated and committed artifacts, and validates the Gemara and Structurizr exports against their
schemas when the tools are present. Inline term linking was made deterministic so the drift check is
stable.

=== Consequences

- The generation gates are load-bearing: a broken model or a stale committed document fails CI.
- Generated artifacts are deterministic and reproducible from the model.
- One script is the source of truth for local pre-commit checks and CI.

[[ADR-EMG-014]]
== ADR-EMG-014: Apply model deltas through YAML nodes and typed candidate validation

Status:: accepted
Date:: 2026-09-15

=== Context

Local change workflows need deterministic add, update, and remove operations without making
agents rewrite complete model documents. Marshaling the typed Go structs would rewrite unrelated
YAML, drop comments, and emit zero-value fields, while text patches would bypass model semantics.

=== Decision

Apply stable-ID operations to yaml.Node trees, preserving unchanged nodes and comments. Decode the
merged candidate into the existing typed model and run the existing structural and EARS validators
before permitting an atomic same-directory replacement. Begin with requirements.yml and whole-entity
updates; extend the same contract to other authored documents after the vertical slice is proven.

=== Consequences

- Change diffs stay focused on intended entities instead of reformatting the complete document.
- Existing model validation remains the authority for candidate correctness.
- Updates replace complete requirement entities rather than applying ambiguous field-level patches.
- The first schema version mutates requirements only.

[[ADR-EMG-015]]
== ADR-EMG-015: Make SysML and KerML semantics canonical without duplicating Engineering Model concepts

Status:: accepted
Date:: 2026-09-18

=== Context

A parallel SysML export schema would duplicate parts, interfaces, flows, requirements, allocations,
and views already authored in the Engineering Model. It would allow the two representations to drift
and still would not establish SysML abstract-syntax or semantic conformance.

=== Decision

Keep YAML as the canonical authoring and persistence format, while evolving its schema and the typed
in-memory model toward the SysML v2 and KerML abstract syntax. The current YAML schema may be accepted
through a migration adapter, but it is not a second semantic authority. SysML textual syntax is an
output, not the canonical input. Every standard concept has one canonical representation shared by
validation and all exporters. Threat, compliance, risk, POA&M, ADR,
repository-composition, code-ownership, and verification-evidence concepts remain typed extensions.
The SysML exporter must report unsupported or lossy mappings and must not claim semantic-superset
conformance until executable coverage and round-trip checks cover the normative language.

=== Consequences

- YAML remains the authored source of truth, but its schema may change as the canonical semantic model matures.
- SysML textual syntax and project interchange remain generated outputs.
- Existing document, assurance, traceability, and validation behavior must be preserved through adapters.
- Exporters migrate to one canonical model instead of maintaining format-specific source models.
- SysML conformance claims are evidence-based and distinguish subset export from semantic-superset coverage.

[[ADR-EMG-016]]
== ADR-EMG-016: Use CUE as the schema contract for canonical YAML

Status:: accepted
Date:: 2026-09-18

=== Context

The canonical model needs one maintainable constraint language that rejects unknown fields,
expresses cross-field invariants, and detects drift in runtime representations. Replacing YAML
authoring with a CUE-authored domain model would create a second persistence format and disrupt
existing repositories, while treating Go structs as the schema authority would limit declarative
constraints and external schema reuse.

=== Decision

Keep YAML instances as the canonical authored and persisted model. Use embedded, modular CUE schemas
as the authoritative shape and cross-field constraint contract for every canonical YAML document.
Validate YAML against CUE before strict Go decoding. Treat Go types as runtime API representations
whose YAML fields are checked against the CUE contract, not as a separately authored semantic model.
Do not create a CUE-authored domain instance model. Keep SysML textual DSL as generated output from
the normalized canonical model.

=== Consequences

- Existing YAML authoring workflows and repositories remain compatible.
- CUE validation provides closed schemas, path-aware diagnostics, and cross-field constraints before runtime decoding.
- Tests must fail when CUE document shapes and Go YAML representations drift.
- Schema changes require coordinated CUE, runtime API, fixture, and documentation updates.
- SysML textual DSL remains a projection and cannot become an alternate source of truth.

[[ADR-EMG-017]]
== ADR-EMG-017: Pin the official SysML 2.0 parser baseline and delegate KPAR packaging to Sysand

Status:: accepted
Date:: 2026-09-18

=== Context

SysML project interchange must be externally consumable and its conformance claims must be
reproducible in CI. A hand-built ZIP cannot establish KerML KPAR conformance, an unpinned
installer cannot provide repeatable evidence, and the 2026-08 Pilot Implementation targets
SysML 2.1 Beta 2 rather than the formal SysML 2.0 and KerML 1.0 baseline.

=== Decision

Validate generated source with the official Pilot Implementation release 2026-04, artifact
0.59.0, commit 20897e3122f2c2f8b29389745f0caaaeb7c6e21a, through the
DeciSym/sysmlv2-validator wrapper pinned at commit
63abbd9fbc7851dc437d01b2dc07836b919770b8 and configured with the matching
release tag and artifact version. Delegate project creation, KPAR packaging, and KPAR reopen
to Sysand 0.2.1 at commit 8430ab04d4d825fb1c196670692d2dafa344e713.
Cache all tools under the ignored .engmod tree, verify published release-asset SHA-256
digests, and use immutable Git commits where no separate source-archive checksum is
published. Preserve the canonical semantic model in typed EngineeringProject metadata and
require reconstructed semantic equivalence after reopening the KPAR.

=== Consequences

- CI blocks syntax errors, unsupported or lossy diagnostics, stale generated SysML, KPAR reopen failures, and semantic round-trip differences.
- KPAR files are produced by Sysand and are not custom archives presented as normative interchange.
- Local validation may be explicitly skipped when external tools are deliberately unavailable, while CI must install and run the pinned toolchain.
- Official parser success proves syntax against the selected baseline but does not by itself imply complete semantic conformance.

[[ADR-EMG-018]]
== ADR-EMG-018: Implement NAF 4.1 as a profile over canonical model views

Status:: accepted
Date:: 2026-09-19

=== Context

The NATO Architecture Framework organizes architecture descriptions by stakeholders, concerns,
and viewpoint products. Its capability, service, logical, resource, and architecture concepts
overlap with concepts already represented by the canonical SysML and KerML aligned semantic graph.
Creating a separate NAF domain graph would duplicate those concepts and allow the two models to drift.

=== Decision

Keep capability, service, logical, resource, behavior, interface, and requirement concepts in the
canonical semantic graph. Author only NAF-specific profile metadata in YAML: framework version,
architecture-description identity, stakeholder bindings, concerns, and official NAF viewpoint
selections. Each NAF architecture product references an existing Engmod view, and the NAF exporter
renders that projection with stable canonical identifiers. Validate the profile with CUE and
cross-reference checks before generation.

=== Consequences

- NAF architecture products and existing SysML, Structurizr, assurance, and document outputs share one source of truth.
- NAF viewpoint products cannot introduce private copies of system elements or relationships.
- Adding another NAF release requires an explicit versioned viewpoint registry and validation update.
- Generated NAF documents provide framework-aligned architecture descriptions but do not imply certification by NATO.

[[ADR-EMG-019]]
== ADR-EMG-019: Make the YAML document set self-describing without breaking legacy inputs

Status:: accepted
Date:: 2026-09-19

=== Context

The canonical model is split across architecture, catalog, requirements, design, and decisions YAML.
Only the catalog path was explicit; the remaining companion files were discovered through fixed names,
and none of the documents declared a common schema version. Humans could learn these conventions from
repository history, but an AI agent had to infer them from loader code and multiple schemas.

=== Decision

Add an optional schemaVersion field to every canonical YAML document and explicit companion-document
references under architecture.model.documents. Version 1 is the implicit value for existing inputs.
Keep baseCatalogRef and the established default filenames as compatibility adapters, reject conflicting
old and new catalog references, and expose the resolved document set, schema locations, top-level fields,
stable-ID conventions, and recommended authoring order through a model.authoringContract MCP tool.

=== Consequences

- Existing repositories and all generated output formats remain compatible.
- New models can declare their entire input document set in one discoverable location.
- AI agents can obtain a compact editing contract before reading broad YAML or Go implementation files.
- Future incompatible input changes require a new explicit schema version rather than silent reinterpretation.

[[ADR-EMG-020]]
== ADR-EMG-020: Distribute reusable model systems as CUE modules in OCI registries

Status:: accepted
Date:: 2026-09-19

=== Context

Company-scale engineering models span multiple repositories and products. Shared hardware,
software platforms, security services, and compliance baselines must be reused without copying
their concepts into each product model. Local paths help monorepositories and git references
help source-based integration, but neither provides a standard immutable package distribution
contract with existing registry authentication and caching conventions.

=== Decision

Treat each reusable Engineering Model directory as a CUE module containing cue.mod/module.cue
plus the canonical YAML document set. A subsystem may select a module path and exact semantic
version; the composition resolver uses CUE_REGISTRY and CUE's OCI module protocol to fetch and
cache it. Keep local and git references as compatibility adapters. Add engmod.work.yml as a
development-only replacement map from module identity to sibling repository paths, analogous
to workspace replacement mechanisms in established module ecosystems.

=== Consequences

- Multiple product repositories can consume the same versioned hardware, software, security, and compliance models.
- CI and released products resolve exact OCI module versions while local workspaces can use explicit sibling-repository replacements.
- Published artifacts remain valid CUE modules and can use existing OCI registry authentication and mirroring.
- The resolver must reject ambiguous source declarations, invalid versions, path escapes, and replacement module identity mismatches.

[[ADR-EMG-021]]
== ADR-EMG-021: Derive file references from repository paths instead of authored source artifacts

Status:: accepted
Date:: 2026-10-13

=== Context

Models referenced in-repository source files through hand-authored referenced elements carrying a path,
a commit, and a blob hash. The model and the code are versioned together, so the pinned commit is always
the commit being validated and goes stale on every change, while nothing checked that the path still existed.
Inferred CODE identifiers could not be referenced because they were keyed on symbol names alone and were
only known when generators scanned code.

=== Decision

Give every in-scope file and declaration a CODE identifier derived from its module-relative path, resolve
authored CODE references during validation, and restrict referenced elements to artifacts outside the
repository, where an explicit version still carries information.

=== Consequences

- In-repository files need no authored entries; renaming or deleting a referenced file fails validation.
- Declaration identifiers change from CODE-<NAME> to CODE-<PATH>--<NAME>, so generated trace outputs change once.
- Models that pointed referenced elements at local paths must switch those references to CODE identifiers.

[[ADR-EMG-022]]
== ADR-EMG-022: Requirement links run child to parent and their strictness is a manifest setting

Status:: accepted
Date:: 2026-11-03

=== Context

A composed system must show which child capability or assumption of use satisfies each of its requirements,
and a child must trace its own requirements upward without knowing who uses it. The owner wants the links
required and enforced as errors, but turning the rules on for every model would break every existing model on
upgrade.

=== Decision

A child requirement realizes its own contract items (realizes: [CAP-* | AOU-*]); the using system records
reqLinks entries from its requirements to the dependency items (model/req-links.yml). The manifest setting
requirementLinks: strict | guided (default guided) chooses the severity of the strictness-dependent rules only:
requirement.no_parent, link.aou_unverified and requirement.unsatisfied are errors in strict mode in every model,
and warnings in guided mode where the model publishes contract items or has links. Every other link rule
(link.suspect, link.broken, link.version_mismatch, link.parent_unknown, link.child_unpublished, link.review_unrecorded,
link.fingerprint_outdated, contract.realizer_unpublished, requirement.realizes_unknown) is an error in both modes.
engflow init writes strict. (docs/requirement-links.md D1.)

=== Consequences

- Existing models keep 0 errors on upgrade; new projects get the strict rules from engflow init.
- The direction stays child to parent; no child names a user.
- Amended by ADR-EMG-028; no model is exempt from the upward trace as top level.
- Amended by ADR-EMG-031; with a life-cycle tier the mode is the maximum of requirementLinks and the tier default (strict from mvp), and the strict findings are errors from the tier where the rule is required.

[[ADR-EMG-023]]
== ADR-EMG-023: The using system fingerprints the child item from the content it resolved

Status:: superseded
Date:: 2026-11-03

=== Context

A link must become suspect when the child item or a requirement that realizes it changes. A fingerprint
file written by the child would have to be kept fresh and could disagree with the content the system actually
composed.

=== Decision

The system computes each item's fingerprint itself from the child's published content at the pinned
version: the item and its realizing requirements in canonical form. Every realizer of a published item must be in the
same publication (contract.realizer_unpublished). No generated fingerprint file exists. (D2.)

=== Consequences

- Nothing to keep fresh; the fingerprint always describes the content the system resolved.
- A child cannot keep a realizer of a published item private.
- Superseded by ADR-EMG-030 (D23) for the fingerprint; contract.realizer_unpublished stays.

[[ADR-EMG-024]]
== ADR-EMG-024: A dependency bump re-pins only unchanged links and never re-stamps a fingerprint

Status:: accepted
Date:: 2026-11-03

=== Context

A pin records what was reviewed. Moving it to a new version is safe only when the item content is the same
there; otherwise the change must be reviewed by a person.

=== Decision

engws bump evaluates the links on the bumped alias only, at the new version: unchanged links move
pinned.version, suspect and broken links keep pin and fingerprint, and a suspect or broken link aborts the bump with
every file restored unless --allow-suspect, after which the check fails until engws review-links --accept. bump
never writes a fingerprint. (D8.)

=== Consequences

- A bump cannot silently accept a changed child item.
- Links on other aliases are not touched by a bump; their own pins are checked by validation.
- Amended by ADR-EMG-030 (D23) - bump compares meanings between versions, writes the bump and leaves changed links at their old pin (exit 1 unless --allow-review).

[[ADR-EMG-025]]
== ADR-EMG-025: Used By is a render-time opt-in and is never committed into a child

Status:: accepted
Date:: 2026-11-03

=== Context

A child is reused by systems it must not know about, and its committed documents must not disclose them. A
developer working in a workspace with the users checked out next to the child may still want to see who links its
items.

=== Decision

The AsciiDoc Used By section is off by default, also when a workspace is found, and is rendered only with
AsciiDocOptions.UsedBy (engdoc --used-by). It lists the requirement links of the other checkouts of the active
workspace onto the rendered model's published items, reading only replacement directories inside the workspace,
confined like dependencies; a document rendered with it must not be committed into the child, and the maintained
examples are rendered without it. (D16.)

=== Consequences

- A default render of a child names no user, in or out of a workspace.
- Seeing users is an explicit local act; review of the diff keeps it out of the child's repository.

[[ADR-EMG-026]]
== ADR-EMG-026: The contract item fingerprint is versioned by canonical form

Status:: superseded
Date:: 2026-11-03

=== Context

Adding a field to the canonical form, or normalizing one differently, changes every fingerprint. Without a
version, every link would then report link.suspect although no child changed, and a reviewer could not tell an engine
upgrade from a real change.

=== Decision

A fingerprint is sha256:v<N>:<hex>, N the canonical-form version (1). Any change to the canonical form is a
new version. A recorded fingerprint of an older or unknown version, or the unversioned sha256:<hex> form, is not
compared: it is reported as link.fingerprint_outdated (error, distinct from link.suspect) with the message to check
that nothing changed and re-stamp it with engws review-links --accept, or to use a later engine that migrates the
form. Version 1 covers the item id, kind, text and verificationCriteria and, per realizing requirement, id, text,
notes, verificationCriteria, verificationMethods (sorted), criticality and status; title, rationale, appliesTo,
priority and tags are not covered. (D17.)

=== Consequences

- An engine upgrade that changes the canonical form produces one distinct, explainable finding per link.
- Links recorded by v0.8.0 pre-releases must be re-stamped once.
- Superseded by ADR-EMG-030 (D23); links record no fingerprint.

[[ADR-EMG-027]]

[[ADR-EMG-028]]
== ADR-EMG-028: Every requirement traces upward through a capability; no model is top level

Status:: accepted
Date:: 2026-11-03

=== Context

The first requirement link rules exempted a system marked inferenceHints.topLevel and any requirement with

[[ADR-EMG-029]]
== ADR-EMG-029: model.patch is the one MCP tool that writes, confined to the model's own documents and valid results

Status:: accepted
Date:: 2026-11-03

=== Context

Agents edited model YAML with ad-hoc string replacement scripts: about 25 edits in one session, one of which

[[ADR-EMG-030]]
== ADR-EMG-030: A requirement link records the published version it was reviewed at, not a fingerprint

Status:: accepted
Date:: 2026-11-04

=== Context

The v0.8.0 link fingerprint had no authoring path (the schema required an engine-written value, so links were
written through deprecated allocations and migrate-links), churned on every workspace edit of a child and on a mere
status change, and let a stale module cache report a link as accepted while the next check found it suspect. Every
repeated check printed the item and realizer texts of each suspect link. Published versions are immutable, so the
version a link was reviewed at already identifies the content that was reviewed (simulator-family retro 1104, items
2, 3 and 12; owner decision).

=== Decision

A link is {id, parent | evidence, child, pinned {version}, status claimed|accepted, rationale, reviewedBy,
reviewedOn}. pinned.fingerprint is deprecated: accepted for one release, ignored, reported as
link.fingerprint_deprecated (warning), removed by engws migrate-links. The check compares no content: a pin other
than the dependency pin is link.version_mismatch, an item missing at the published dependency pin link.broken, and a
dependency resolved from a workspace replacement raises no link finding (a checkout has no version). engws bump
compares each link's item and realizing requirements between the pinned and the new published version by meaning
(item kind, text and verificationCriteria; each realizer's text and verificationCriteria) and moves the pin only
when it is the same; status, notes, criticality and the other fields are not compared. engws review-links lists the
links that need review one per line and --show prints before and after; --accept moves the pin to the dependency
pin and re-evaluates the link. engws link add writes a claimed link at the dependency pin after checking parent and
child. Supersedes D2 and D17 (ADR-EMG-023, ADR-EMG-026) for the fingerprint and amends D8 and D9 (ADR-EMG-024).
(docs/requirement-links.md D23.)

=== Consequences

- Editing a child in a workspace never changes a link's state; review happens at a bump, once per release.
- A status or notes change in a child release moves the pin without a review; a note of a capability is its text, so changing it needs one.
- A version re-staged with other content is detected through the registry manifest digest of the cached module and refetched.
- link.suspect and link.fingerprint_outdated no longer exist; trace linksSuspect is a deprecated alias of linksVersionMismatch next to the new linksNeedReview.

[[ADR-EMG-031]]
== ADR-EMG-031: The manifest life-cycle tier selects the severity of the tier rules

Status:: accepted
Date:: 2026-11-05

=== Context

engineering-flow builds a project at one life-cycle tier (poc, prototype, mvp, product, operational) and
raises rigour as the project matures. Raising severities only in the flow's own check left engdoc, engtrace, MCP and
engws check with another answer, and the flow could raise but never defer a rule (tiered development guidance,
sections 6.1 and 6.2).

=== Decision

engmod.yml lifecycle {tier, bundles?, tierDecision?, raise?} is optional. Without it every result is that of
v0.9.0 (golden tests). With it, internal/validate/tier_policy.go keys a closed table of codes by tier (TierPolicy):
each is deferred (a warning with the Deferred flag: evidence debt that is reported and never fails a check), a
warning or an error at the project tier, with requiredFrom; lifecycle.raise makes named codes errors and never lowers.
ApplyTierPolicy runs at every public entry on the merged list (ValidateBundle, GenerateAsciiDoc, the trace
builders, engws check, MCP); it is idempotent, so applying it again at an outer entry changes nothing. Rank-0 core
codes (CoreCodes, a closed list) and every code the table does not key keep their severity at every tier. tierDecision
must name an accepted DEC-TIER-* whose Tier: and Bundles: lines agree (lifecycle.tier_decision_mismatch). Tiers are per
module, never per functional unit or requirement. Amends ADR-EMG-022: the requirement link mode is the maximum of
requirementLinks and the tier default (guided below mvp, strict from mvp), so the strict findings are errors from the
tier where the rule is required; requirementLinks guided at mvp or above is lifecycle.requirement_links_conflict.
Amends ADR-EMG-028: a deferred finding is reported, not exempted; the upward-trace rule holds at every tier and only
its severity is keyed. The life-cycle tier is unrelated to the requirement and system levels ADR-EMG-011 excludes:
it is a property of the module's rigour, never of a requirement. engtrace --tier-gap and MCP tier.gap report what a
target tier requires.

=== Consequences

- Every consumer of the engine gives one result for a tier; engineering-flow renders the table from TierPolicy() instead of keeping its own.
- A project can declare a low tier and see its debt as deferred findings instead of failing on rules it has not reached.
- A low tier cannot hide integrity errors; rank-0 codes and untiered codes never change.

[[ADR-EMG-044]]
== ADR-EMG-044: The machine model is a breaking v0.11.0 release with a full hand rewrite of the repo model and examples

Status:: proposed
Date:: 2026-11-12

=== Context

The plan (non-goals) kept the existing behavior relationships as a migration input. The owner decided against any
compatibility path. The Quint toolchain adds third-party tools to CI: quint (npm), Apalache and a JDK.
Settled in a grilling session with the owner on 2026-11-12. OWNER items: the version number and the supply-chain approval.

=== Decision

The release is v0.11.0 and is breaking: there is no opt-in mode and no automatic migration. The owner rewrites all
models by hand: this repository's own model and every example under examples/ are rewritten in the same effort, so
every model in scripts/validate-all.sh uses machines: when the release is cut. Supply chain: quint 0.33.1 (npm),
Apalache 0.62.4 (tarball sha256 8ac8488422c30d552735bae11b92a2d014d8e02e8608702acc08f9a2d8a9abb2) and Temurin JDK 21
are approved for CI. Owner statement, verbatim, 2026-11-12: "all the tools are approved use them in CI even if you cannot
install them here now." Pin versions and check the download sha256 in CI. Covers REQ-EMG-139, REQ-EMG-144.

=== Consequences

- Models written for v0.10.0 do not validate until rewritten; the CHANGELOG says so.
- CI installs the three tools with scripts/install-quint-toolchain.sh (pinned versions, sha256-checked Apalache, quint from a lockfile with --ignore-scripts). The development environment of this change installs the same pins under .engmod/tooling; tests that run quint skip when ENGMOD_QUINT is unset, and the runner is also tested against a fake quint.

[[ADR-EMG-045]]
== ADR-EMG-045: Implementation decisions taken during the machines and Quint work, recorded as proposed

Status:: proposed
Date:: 2026-11-12

=== Context

The owner asked for the work to continue without questions, taking the recommended option and documenting each choice
as an ADR. These choices were made by the implementing agent while building REQ-EMG-135..149 and have not been
reviewed by the owner. They are all OWNER items.

=== Decision

(1) Machine IDs match SM-[A-Z0-9-]+; state, transition and invariant IDs keep the stable-ID pattern, and the machine
state IDs keep the STATE-* form. (2) The expression tree marks every node with a kind: operator, literal, variable or
reference. A variable leaf is a scalar value (the variable name), not a typedValue reference, because a reference must
resolve to a model element. (3) An effect always parses to an all node, even for one assignment. (4) Empty string
literals are rejected by the parser and by the variable initial value, because the semantic value type cannot represent
an empty string. (5) Invariants are named after their own INV-* ID (val inv_<snake id>) and the results map the
invariant to its requirements through the model; there is no combined inv_all, so each invariant is checked and
reported alone. (6) A state constructor in the generated Quint type is the PascalCase form of the whole state ID, so it
is unique and stable; a collision after sanitising is a generation error. (7) Reachability is computed from the
machine's declared initial state; the first-declared-state heuristic of v0.10.0 is dropped. (8) A document that still
uses behavior.states, transitions_to or a state triggered_by fails to load with a message naming machines and
ADR-EMG-038. (9) A construct that SysML v2 cannot express validly is exported as a comment and reported as a
sysml.machine_construct_commented warning, never as invalid text. (10) Quint is always called with --backend=typescript
and engquint never downloads a tool.
(11) Quint 0.33.1 has no string escapes, so a string value containing a double quote, a carriage return or a line feed
cannot be generated and is a generation error (quint.unsupported_string); other strings are emitted raw. (12) A
single-state machine is emitted as `type State = | X`, because Quint reads the form without the bar as a type alias.
(13) The runner is the subpackage internal/export/quint/check, so its exported names are not part of the root facade;
cmd/engquint imports it directly. (14) quint verify reports a deadlock as a violation, which would fail every machine
with a final state, so verify runs with an Apalache configuration that sets no-deadlock; run mode reports a deadlock at
the initial state as a warning and a zero-length trace as an error. (15) A violated invariant is written to the evidence
file as a failing entry, so a requirement whose only invariant fails is failed and not unverified. (16) A stale formal
result is a not-run result with a verification.formal_stale warning; the scan compares the sha256 of the named .qnt file
with the recorded one. (17) A counterexample lists the ordered TR-* IDs and omits the initial state. (18) SysML export
renders a machine as a state definition with entry, transitions with accept, if and do, and invariants as constraints;
in_state has no SysML expression form, so a guard, effect or invariant using it is exported as a comment. (19) A
machine variable whose name is a SysML keyword is quoted, and one that collides with a name the state definition
inherits gets a _var suffix and a comment with the authored name.
(20) Formal evidence rolls up per requirement as failed over pass over stale over not-run (internal/trace
formal_evidence.go). A current failing result makes the requirement failed: the formal check stays linked, the row result is
failed, the row status is unchanged (verified when no code implements it) and verification.failed names the machine and
invariant in a model with lifecycle. A current passing result is analysis evidence: the formal check is a linked
verification, so a requirement without code is verified, and the row result is passed unless a linked test fails. A stale
or not-run result is no evidence: the requirement is removed from the formal check before any roll-up, so it neither
verifies nor fails the requirement, does not downgrade a requirement another passing test or current invariant verifies, and
a requirement with only stale results stays orphan, with the warning verification.formal_stale from the scan. Status
inference is otherwise unchanged and a row without formal evidence is byte-identical. (21) Trace rows gain two additive
fields, both omitted without formal evidence: evidenceMethods (analysis, plus test when a test is also linked) and formal
(one entry per invariant result with machine, invariant, mode, result, qntFile, qntSha256, evidence file and notes, stale
entries included); the CSV columns are unchanged. (22) The codescan check carries no machine, invariant or hash, so
internal/trace re-reads the evidence files named in the formal check's evidence and recomputes staleness with the codescan
rule; the Gemara exporter, which the layering keeps from importing the trace, mirrors that reader and the MCP tools read the
results from the trace matrix rows. (23) The Gemara evaluation log gets one
ControlEvaluation per requirement with formal evidence: its control is the requirement under the mapping reference
ENGMOD-REQUIREMENTS (declared in the metadata only when formal evidence exists), each assessment log maps the invariant ID,
pass is Passed, fail is Failed, a stale or not-run result is Not Run with the reason in the message, and the evidence
(type FormalVerification) carries machine, invariant, mode, method analysis, qntFile and qntSha256 in a payload map; only
fields the control entries already use are written. The cue vet of scripts/validate-gemara.sh could not run offline, so the
structure is checked with the SDK type detection and in-repo invariants; the evidence file is searched under the model
test-results directory and beside the code root, and the entries reach the OSCAL assessment results through the same log. The Gemara cross-reference check treats the declared ENGMOD-REQUIREMENTS reference as external, since the requirements are not a rendered Gemara artifact.
(24) MCP verification.status gains formalResults (requirement, rolled-up result pass, failed, stale or not-run, and each
invariant result), narrowed by entityId or id naming a requirement, machine or invariant; verification.gaps gains formalGaps
(requirements whose result is not pass); trace.matrix rows gain formal and evidenceMethods; the results are read live from
the model test-results directory through the trace matrix (a model without an evidence file skips that build), only for requirements of the model, and every key is absent without formal evidence. (25) model.authoringContract moves to
engineering-model.authoring.v3 with a machines section (expression grammar, type rules, the operator table generated from
the table the parser and Quint generator share, the engquint workflow and the evidence semantics) and the SM, TR and INV
identifier prefixes; the field sets and the machine diagnostics stay in rules. (26) The tier-gap listing of the Quint
requirements by tier (ADR-EMG-043) is deferred to engineering-flow's gate steps: the operational rule needs the machines
of functional units in safety or mission flows, and flow kind and criticality are free text the model does not classify,
so tier.gap does not list them.
(27) The initial state of a machine is never reported as an unreachable state by the runner, because Quint's witness
count does not include the state a trace starts in; the witness count is still recorded as is. (28) The script
scripts/lifecycle-golden-self.sh is retired: it compared the repository's own model with the v0.9.0 engine, which cannot
load models that use machines, and no gate ran it. The no-lifecycle golden over the examples stays and was regenerated.
(29) The Gemara, compliance and security outputs under generated/ are left as committed: they were already behind the
engine, the freshness gate does not regenerate them, and regenerating them would bury the machines change in unrelated
differences. (30) Published machines and machine states are not merged into an importing model on composition; merging
needs qualified expressions and is left for a later release. (31) model.State is kept as a deprecated alias of
model.MachineState for one release, so the public facade does not break in the same release that removes behavior.states.
(32) engws release-check and contract-diff read the model of an earlier tag only for its contract (requirements and
interfaces). They load a behavior document committed before v0.11.0 with the retired state vocabulary stripped
(model.StripLegacyStateVocabulary), so the release check of the first tag after the removal does not fail on the previous
tag; the working tree is still refused.

=== Consequences

- Each choice can be changed by a later ADR without changing the authored YAML form, except (1) and (2).
- Choice (4) means a String variable cannot start empty; use a one-character sentinel or an Integer or Boolean encoding.
- The owner should review this ADR before the release is tagged.
