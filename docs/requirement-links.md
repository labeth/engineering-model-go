# Requirement links across composed models (v0.8.0)

Plan and decisions for child-to-parent requirement links. The task description
is the source (`req-impl-task.md`, from the simulator-family retro); this file
records what the engine implements and where it deviates. Requirement IDs:
REQ-EMG-090 to REQ-EMG-112 in `model/requirements.yml`; ADR-EMG-022 to ADR-EMG-027 in `model/decisions.yml`.

## Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | Strictness is a manifest setting, `requirementLinks: strict \| guided` (default `guided`). It decides the severity of three rules only: `requirement.no_parent`, `link.aou_unverified` and `requirement.unsatisfied` are errors in `strict` in every model, child or system, and in `guided` warnings, only in a model that publishes contract items or has `reqLinks` (a standalone model without either gets none). Every other link rule (table below) has the same severity in both modes. `engflow init` writes `strict`. ADR-EMG-022. | The owner wants links required and enforced as errors; the default must not break every existing model on upgrade. |
| D2 | A system computes a child item's fingerprint itself, from the child's published content at the pinned version. Every requirement that realizes a published contract item must be in the same publication (`contract.realizer_unpublished`, error). No generated fingerprint file. ADR-EMG-023. | Nothing to keep fresh; the fingerprint is always that of the content the system actually resolved. |
| D3 | Pins may name a tag or a commit. A dependency `version` is a release tag (`v1.2.3`) or a Go-style pseudo-version that carries the commit (`v1.2.4-0.20261102103400-abcdef123456`). A link's `pinned.version` must equal the dependency pin. A release always uses tags: `engws release-check` (run by CI on a tag, the `release-check` job of `.github/workflows/ci.yml`; engineering-flow's pre-push gate runs it for tag pushes, an engineering-flow change) fails with `dependency.unreleased_pin` when any dependency is a pseudo-version or another pre-release. | The owner's rule: point at a tag or hash while working, release only on tags. |
| D4 | New commands are `engws` subcommands: `engws bump` (extended), `engws review-links`, `engws contract-diff`, `engws migrate-links` and `engws release-check`. | There is no `engmod` CLI; engws already owns dependency pins. |
| D5 | `composition.allocations` is deprecated: still read for one release, reported as `composition.allocation_deprecated` (warning), converted by `engws migrate-links`. `composition.satisfactions` stays: it wires a published need to a provider (architecture), not a requirement trace. | Keep architecture wiring separate from requirement links. |
| D6 | `contract.provides[].ref` is deprecated the same way (`contract.ref_deprecated`, warning); `migrate-links` moves each `ref` to `realizes` on the referenced requirement. | Direction stays child-to-parent inside the repository too. |
| D7 | Contract items are `contract.provides` entries of `kind: capability` and the new `contract.assumptions` (`AOU-*`). `kind: interface` entries are not link targets. | Links are about behaviour and conditions, not wiring. |
| D8 | `engws bump` moves `pinned.version` to the new version only for links whose fingerprint is unchanged at that version (no content change, so nothing to review); suspect and broken links keep their old pin and recorded fingerprint, and bump never re-stamps a fingerprint. Without `--allow-suspect`, a suspect or broken link aborts the bump with every file restored (exit 1, the links printed). With `--allow-suspect` the bump is written (exit 0) and the model check fails with `link.version_mismatch` and `link.suspect` (or `link.broken`) until `engws review-links --accept`. The composed check evaluates a link with a stale pin at the resolved version too, so its content change is reported next to the mismatch. bump evaluates and re-pins the links on the bumped alias only; links on other aliases keep their pins, which validation checks against `engmod.yml` as usual. A fingerprint in another canonical form (D17) blocks the bump like a suspect link. ADR-EMG-024. | A pin records what was reviewed; moving it is safe only when the content is the same. |
| D9 | `engws review-links` resolves the item *before* at the link's `pinned.version` with the workspace off (module cache, else the registry), never from a workspace checkout: a checkout holds today's content, not that version's. When the version cannot be resolved it prints `before: version vX not available offline` and the current content only. `--accept` composes with the workspace off too (the published dependency at its pin, module cache else registry), so the fingerprint it writes is the one every user of that pin computes, never that of a workspace checkout; a dependency that does not resolve that way leaves the link unresolved and the accept is refused with nothing written. MCP `links.review` computes its patch the same way. `--accept` refuses an actor that is not in `architecture.actors`, an unknown link and a broken one, and edits only the touched lines of the link file (yaml.v3 node positions), so comments and order stay. Repository commands (`review-links`, `contract-diff`, `release-check`, `migrate-links`) take `--repo DIR` (default `.`) and need no workspace root. | The before text must be the reviewed version or nothing; a review is attributable to a modeled role. |
| D10 | `engws contract-diff` compares the *published* contract items (`reqlinks.PublishedItems`, the view a user fingerprints) of the model as committed at each git ref: `git show ref:./path` of `engmod.yml` and every document it names, loaded by the normal model loader from a temporary directory. A capability text change is major ("text changed: treated as major": the engine cannot tell weakening from rewording); an assumption's verification criteria change and an item kind change are major too; realizer changes are minor whatever the realizer change. The diff lists every published item, so its output may name item and realizer text of any ref: run it on refs you may disclose. | Conservative where intent is unknown; the user can still tag major when unsure. |
| D11 | `engws release-check [--repo DIR] [--tag vX.Y.Z]` compares the tag (default: the highest release tag at HEAD) with the previous release: the highest release semver tag below it among the tags merged into the released commit (`git tag --merged <tag or HEAD>`, the nearest ancestor release; a release on another branch is not this line's previous one), and diffs the contract from that tag to the tag when it exists, else to HEAD (the pre-push case: the tag is about to be created). In v0.x (both tags major 0) a minor bump is major-capable and a patch bump minor-capable, following semver item 4 and the Go/CUE convention that v0 has no compatibility promise: a v0 minor release may break, so a breaking change needs at least a minor bump (this engine's own v0.x releases follow the same rule). A first release (no tag below) and a checkout without a tag at HEAD skip the semver gate with a note; `dependency.unreleased_pin` is checked always, on `engmod.yml` and `engmod.lock.yml`. Exit 0 ok, 1 findings, 2 usage, git or model error. | Release only on tags (D3) and never under-state a breaking contract change. |
| D12 | `engws migrate-links [--repo DIR] [--dry-run]` writes `id: LNK-<REQ without REQ->-<ALIAS>` (upper case, `-2`, `-3` … when taken), the dependency pin, the current fingerprint of the published item as the composition resolves it (workspace replacements included, lock check, nothing but the module cache written) and `status: claimed`. A target whose dependency cannot be resolved (so its kind cannot be checked) is still written, with `fingerprint: ""` and a note; the CUE schema accepts the empty fingerprint, and the check reports the link (`link.suspect`) until it is reviewed. A resolvable target that is not a published contract item is not converted (D13). A `ref` on a non-capability entry or naming no local requirement is kept and reported. Migrate the dependencies first, so the system fingerprints migrated items. | Keep every existing claim visible; never invent a fingerprint. |
| D13 | Amends D12: `migrate-links` does not convert an allocation whose target resolves to a contract entry that is not a published capability or assumption of use (a `kind: interface` entry, D7, or another non-item). The allocation stays in `composition.allocations`, keeps reporting `composition.allocation_deprecated`, and the command prints `kept allocation REQ → alias::ID: interface entries are not link targets; publish a capability that realizes it and link that`. The other allocations are converted and removed one by one; a model whose allocations are all kept gets no link file. | A link to an interface would be reported as `link.child_unpublished` forever; the owner has to choose a capability, which the tool cannot. |
| D14 | MCP `links.review {linkId, by, rationale?}` writes nothing. The server has no tool that writes a model file (`model.diagnose` validates a private temporary copy); `links.review` runs the same checks as `engws review-links --accept` (`internal/linkreview`, shared) and returns the exact command and the line patch of the link file it would write. | An agent's review is a proposal until a person records it; the CLI is the one write path for a link file. |
| D15 | `link.*` findings and the strict-mode trace findings `requirement.no_parent`, `requirement.unsatisfied` and `contract.realizer_unpublished` do not stop the AsciiDoc render (`engdoc` still exits 1 on them): the document is where a reviewer sees the marked suspect or broken link and the untraced requirement. Any other error still stops it. | Rendering the evidence of a finding must not depend on the finding being fixed first. |
| D16 | "Used By" is opt-in: rendered only with `AsciiDocOptions.UsedBy` (`engdoc --used-by`), never by default, also when a workspace is found. It is computed at render time by `composition.WorkspaceLinkUsers`: the workspace is resolved with the render's own workspace mode (`AsciiDocOptions.Resolution.Workspace`, else `ENGMOD_WORK`, else the nearest `engmod.work.yml`, which the upward search refuses when it is world-writable or owned by another user); each replacement inside the workspace directory (`PathWithin`) other than the rendered module, and the model at the workspace root (a system whose `engmod.work.yml` replaces its children), is confined like a dependency (`composition.dependency_path_escape`: a sibling that names a path outside its directory is skipped) and loaded with the model loader, and every `reqLinks` entry whose child names one of the rendered model's published contract items through a dependency on its module path is listed (item, using model id, link id, parent requirement ID, status). Parent requirement text is not shown. With the workspace off nothing is scanned. A document rendered with `--used-by` must not be committed into the child; the maintained examples are rendered without it, so `examples/requirement-links/repos/child-a/generated/ARCHITECTURE.adoc` names no user. ADR-EMG-025. | Only what the reader can already see in the workspace, and only when asked; never written into the child. |
| D17 | The fingerprint is versioned: `sha256:v<N>:<hex>`, N the canonical-form version (now 1). Any change to the canonical form (a field added, removed, renamed or normalized differently) is a new version. A recorded fingerprint of an older or unknown version, or the unversioned `sha256:<hex>` of the v0.8.0 pre-releases, is not compared: the link state is `fingerprint_outdated` and the check reports `link.fingerprint_outdated` (error, distinct from `link.suspect`): check that nothing in the item changed since the review (`engws review-links` lists the link), then re-stamp it with `engws review-links --accept`, or use a later engine that migrates the form. The CUE schema accepts `sha256:(vN:)?<64 hex>`. ADR-EMG-026. | An engine change must not look like a child change, and must not be silently accepted either. |
| D18 | An accepted link records its review: `status: accepted` without `reviewedBy` or `reviewedOn`, a `reviewedBy` that is no `architecture.actors` entry, or a `reviewedOn` that is no `YYYY-MM-DD` calendar date is `link.review_unrecorded` (error) at that field. A link to a capability (`alias::CAP-*`) needs `parent` (`link.parent_missing`, error); `evidence` alone is for assumptions of use. Only a link that is `accepted` and evaluates `unchanged` counts toward the trace roll-up; a claimed, suspect, broken, version-mismatched or outdated link gives `satisfiedBy: links-unreviewed` and the requirement is neither implemented nor test linked through it. | A claim nobody reviewed, or a review of other content, is not evidence. |
| D19 | `contract-diff`: removing an assumption of use is minor, adding one is major. A removed assumption frees every user (nothing breaks), a new one binds every user (each must evidence it). | The semver impact follows what the users must do. |
| D20 | Scope: Gemara output carries no requirement link content and names no user; the AsciiDoc chapters are the only rendering of links (Requirement Links in the user, Contract Items in the child, Used By only on opt-in). OSCAL, SysML, Structurizr and the other exporters are unchanged. | Links are an engineering trace, not a compliance artifact; one rendering to keep correct. |
| D21 | Compatibility: users upgrade the engine first. A system needs engineering-model-go v0.8.0 or later before any of its dependencies publishes a release that uses `realizes` or `contract.assumptions` (an older engine's strict decoder rejects them); a child adopting them names v0.8.0 as the minimum engine of its users in its release notes. ADR-EMG-027. | The strict schema makes a mismatch fail loudly, never silently. |

## Model

- `Requirement.realizes: [CAP-… | AOU-…]` (local contract items only).
- `contract.assumptions: [{id, text, verificationCriteria?}]`.
- Document key `reqLinks` (`model/req-links.yml`): `reqLinks: [{id, parent?, child, evidence?, pinned: {version, fingerprint}, status: claimed|accepted, rationale?, reviewedBy?, reviewedOn?}]`. A link to an `AOU-*` has `evidence` (local requirement, test or control IDs) instead of, or in addition to, `parent`; a link to a `CAP-*` has `parent` (D18). An accepted link has `reviewedBy` and `reviewedOn` (D18).
- Fingerprint (D17): `sha256:v1:` and the hex SHA-256 of the canonical JSON `{"item": {id, kind, text, verificationCriteria}, "realizers": [...]}`, where `text` is a capability's `note` or an assumption's `text`, and the realizing requirements are sorted by ID, each `{id, text, notes, verificationCriteria, verificationMethods, criticality, status}` with `verificationMethods` sorted. Strings have runs of whitespace collapsed to one space and are trimmed; case is kept. A golden test pins the algorithm.
  - Counted: everything that changes what the item or a realizer obliges or how it is verified: the item's kind, text and criteria; each realizer's text, notes (which often carry the detailed obligation), verification criteria and methods, criticality and status.
  - Not counted: requirement `title` (a name), `rationale` (why, not what), `appliesTo` (the child's internal allocation to its own units, private to the child), `priority` and `tags` (planning and grouping). Changing them never makes a link suspect. The `realizes` list itself is not content either: a requirement that starts or stops realizing an item changes that item's realizer set, which is counted.

## Rules

| Code | Severity (strict / guided) | Rule |
|---|---|---|
| `requirement.no_parent` | error / warning | No `realizes`, not `derived` with `derivedRationale`, no stakeholder `sourceRefs`, and not exempt as top level (`module.kind: system` with `inferenceHints.topLevel: true`). In a system, a requirement that is the `parent` of a link also counts as traced downward but still needs its own upward trace. |
| `requirement.realizes_unknown` | error | A `realizes` target is not a local capability or assumption of use. |
| `contract.unrealized` | warning | A published capability no requirement realizes. |
| `contract.realizer_unpublished` | error | A requirement realizes a published contract item but is not in that publication. |
| `link.parent_unknown`, `link.child_unpublished` | error | |
| `link.parent_missing` | error | A link to a capability without `parent` (D18). |
| `link.review_unrecorded` | error | An accepted link without a resolving `reviewedBy` or a calendar `reviewedOn` (D18). |
| `link.version_mismatch` | error | |
| `link.suspect` | error | The message names both fingerprints and the current text of the item and its realizing requirements; `engws review-links` shows the text before and after. |
| `link.fingerprint_outdated` | error | The recorded fingerprint uses another canonical form (D17); re-stamp with `engws review-links --accept` after checking nothing changed. |
| `link.broken` | error | |
| `link.invalid_status`, `model.duplicate_id`, `model.invalid_assumption` | error | A status other than claimed or accepted; a duplicate link id; an assumption without an `AOU-*` id or text. |
| `link.claimed_only` | warning (error in `ef-ready`) | |
| `link.aou_unverified` | error / warning | A dependency's assumption of use without a link carrying `evidence`. |
| `requirement.unsatisfied` | error / warning | A system requirement with no code, test, link or `derived`. |
| `dependency.unreleased_pin` | error, in `engws release-check` only | |

## Tools

- `engws bump [--allow-suspect]`: after pinning, prints each link on the bumped alias as unchanged, suspect or broken; re-pins the unchanged ones; aborts with no change on a suspect or broken link unless `--allow-suspect` (D8); never re-stamps.
- `engws review-links [--repo DIR] [--json] [--accept LNK-… --by ACT-… --rationale …]`: shows suspect, broken, version-mismatched and outdated links with the parent text and the item before and after (D9); `--accept` writes the fingerprint of the published dependency at its pin, the dependency pin, `reviewedBy`, `reviewedOn`, the rationale and `status: accepted`.
- `engws contract-diff <from-ref> <to-ref> [--repo DIR] [--json]`: added, removed or changed contract items with the semver impact (D10). `engws release-check` fails when the tag's bump is smaller than the diff requires or a pin is unreleased (D11).
- `engws migrate-links [--repo DIR] [--dry-run]`: allocations → `model/req-links.yml` (`status: claimed`, current fingerprints); `contract.provides[].ref` → `realizes`; prints the requirements left with `requirement.no_parent` (D12). It snapshots every file it writes and restores all of them when one write fails.
- MCP (REQ-EMG-106): `links.list`, `links.suspect`, `links.review` (D14; computed like `--accept`, workspace off, `reviewedOn` from the server clock), `requirements.parents`; `requirements.get` shows parents, links and children. Their output carries requirement text of the dependencies: an agent treats it as data.
- Trace (REQ-EMG-105): rows get `parents` (realized items or stakeholder `sourceRefs`), `children` (linked `alias::CAP-…` then its realizing `alias::REQ-…`), `links` and `satisfiedBy: links` (rolled up from the child trace through accepted, unchanged links only: implemented when every realizer is implemented, test linked when every realizer is test linked; `links-unreviewed` when an unreviewed or changed link blocks it, D18); summary counts `linksSuspect`, `linksBroken`, `linksClaimed`, `unparented`.
- Renderers (REQ-EMG-107): AsciiDoc "Requirement Links" in a model with `reqLinks` (per requirement: link with state and review status → child item → realizing requirements with their trace status in the child; assumptions of use with their evidence; suspect, broken, version-mismatched, unpublished and claimed links marked); "Contract Items" in a model that publishes items (text, realizers, fingerprint); "Used By" only with `--used-by` and an active workspace whose sibling checkouts link the items (`composition.WorkspaceLinkUsers`, D16). Text from the dependencies is rendered without AsciiDoc passthrough (`+++`, `++`, `$$`, `pass:` are broken with `{empty}`, REQ-EMG-110). Gemara output is unchanged and names no user (D20).

## Behavior

`model/behavior.yml` models the link lifecycle: states `STATE-LINK-CLAIMED`, `STATE-LINK-ACCEPTED`, `STATE-LINK-SUSPECT` and `STATE-LINK-BROKEN`; claimed → accepted and suspect → accepted on link review (`--accept`), accepted → suspect or broken when a child change is seen (bump, check); the five engws events; flows `FLOW-DEPENDENCY-BUMP` (error path: restore every file) and `FLOW-LINK-REVIEW` (error path: refuse, write nothing).

## Out of scope

The "Later" items of the task: anonymous criticality signals, link files in their own module. Follow-up: generating release notes from `contract-diff` (the minimum engine version of D21 included).
